如何用提示詞引導 AI 做出優秀的軟體設計：把提示詞寫成一份小型設計任務書

只寫「現代、簡潔、有高級感」，AI 往往只能交出好看卻不經用的介面。本文提出把提示詞寫成設計任務書：使用情境、核心任務、約束、取捨規則、交付物和驗收方式，並要求覆蓋載入、失敗、舊結果、重複提交與逾時等狀態。依據 Nielsen 啟發式、WCAG、HTTP 規範等公開資料整理，屬於工程判斷，沒有模型對照實驗。

核心觀點

「做得高階一點」這類風格詞，無法讓 AI 做出好的軟體設計。把提示詞寫成一份小型設計任務書：寫清使用情境、核心任務、約束、取捨規則、交付物和驗收方式，並要求覆蓋失敗、逾時、重複提交等正常流程之外的狀態。這樣設計判斷才能被檢查。這是一種協作方法，不能保證模型輸出品質。

適用物件與邊界：面向用 AI 設計頁面、內部工具和資料看板的工程師與產品人員。本文的方法和提示詞模板是工程判斷，沒有做過不同模型的對照實驗。涉及的通用規範和技術事實附有來源，查核日期 2026-11-12（Asia/Singapore）。文中的監控台案例是虛構場景。

我們讓 AI 設計軟體時，經常寫下這樣的要求：

「請做一個現代、簡潔、專業、有高級感的頁面。」

生成的結果常有大標題、漸層、卡片、圓角和漂亮的圖表。第一眼不錯，真正使用時才暴露問題：

  • 最重要的異常藏在摺疊區。
  • 重新整理後篩選條件丟失。
  • 查詢失敗顯示成零。
  • 連續點選按鈕，建立了兩個任務。

這些問題不需要更複雜的視覺技術，需要更明確的設計判斷。

本文提出一套可操作的方法：把提示詞寫成一份小型設計任務書，說明誰要完成什麼任務、哪些約束不能違反、哪些狀態必須處理，以及如何檢驗結果。這與提示詞工程的一般建議一致：指令越具體，結果越好，因為模型缺少你的背景和習慣。[12]

一、為什麼「高級感」無法直接轉換成好設計#

「高級」描述的是感受，沒有指定如何取捨。

品牌展示頁可能需要大圖和留白。值班人員使用的監控台，更需要資訊密度、異常定位和穩定的佈局。同一種視覺手法，在不同任務裡效果不同。

只給風格詞時，AI 仍然要決定頁面結構、重點和行為。需求沒有給出判斷依據，這些決定就容易落入常見模板。這是對失敗模式的推測，不是實測結論。

可以把風格要求轉換成可觀察的結果：

模糊要求更具體的設計要求
簡潔首屏突出當前最需要處理的問題，低頻設定收進次級區域
專業說明資料口徑、單位、時間範圍和更新時間
現代排版和元件保持一致，操作回饋及時，窄螢幕下可完成主要任務
高級字型、顏色和間距有明確層級，裝飾不干擾閱讀
好用使用者能完成關鍵流程，失敗後知道當前狀態和恢復方法

這樣轉換不是消滅審美，而是讓審美有服務對象。

一個頁面可以很漂亮，同時不適合它的使用者。設計評審要同時回答兩個問題：看起來如何，用起來會發生什麼。

二、設計能力體現在取捨，而不是功能數量#

以一個 ETL 監控頁面為例。需求可能包含任務狀態、延遲、執行記錄、資料量、負責人、告警規則和 SQL 明細。

把它們平均分成八張卡片，形式上很完整，卻沒有回答值班人員最關心的問題：

現在是否有異常，影響了什麼，下一步應該檢查哪裡？

圍繞這個問題組織頁面，結構可以是：

  1. 頂部展示需要處理的異常及影響範圍。
  2. 主列表展示任務狀態、延遲和最近成功時間。
  3. 選擇任務後，檢視執行歷史、失敗明細和恢復操作。
  4. 告警規則、負責人等低頻設定放在獨立入口。

這是一種任務優先順序判斷，不是唯一正確答案。如果使用者的主要工作是批次設定規則，頁面結構就要調整。

所以提示詞要先交代使用情境：

請設計一個 ETL 監控頁面。

主要使用者是值班資料工程師。他們通常在收到告警後開啟頁面，
需要盡快確認異常是否仍在發生、哪些任務受影響、接下來檢視哪裡。

優先支援這三項任務：
1. 找到當前需要處理的異常。
2. 檢視異常任務最近一次成功和失敗的記錄。
3. 判斷是否需要重試，並了解重試可能產生的影響。

請按任務的重要性安排頁面，不要求所有功能都出現在首屏。
說明關鍵內容為什麼放在當前位置，並給出可實作的介面方案。

好的上下文不一定很長，但要包含會改變方案選擇的資訊。

三、把提示詞組織成一份設計任務書#

一份實用的設計提示詞，可以包含六個部分。

部分要回答的問題寫得不好的例子寫得好的例子
使用情境誰在什麼情況下使用後台管理系統值班工程師，收到告警後開啟，時間緊
核心任務使用者最終要完成什麼展示任務資訊判斷昨晚批處理是否按時完成
約束哪些邊界不能突破盡量少改沿用現有元件庫，不改後端介面
取捨規則衝突時優先什麼各方面都做到最好修改資料的操作，優先保證結果可確認
交付物希望拿到什麼給個方案狀態表加可執行原型
驗收方式怎樣確認成立體驗流暢查詢失敗後不顯示零值，篩選條件保留

1. 使用情境#

「後台管理系統」仍然太寬泛。每天使用八小時的工作台，和每月只開啟一次的設定頁，適合不同的資訊密度和引導方式。

只寫與當前設計有關的條件：使用者熟悉程度、使用頻率、裝置和時間壓力。

2. 核心任務#

「展示任務資訊」是功能描述。「判斷昨晚批處理是否按時完成」才是使用者任務。

任務越清楚，越容易判斷哪些元件必要，哪些資訊要突出。

3. 約束#

例如沿用現有元件庫、不修改後端介面、保持指標口徑、支援現有權限模型。

約束要具體。不能一邊要求最小改動，一邊預設允許重構整個產品。

4. 取捨規則#

資訊完整與首屏簡潔、操作速度與誤操作防護、即時性與系統成本，都可能衝突。

「所有方面都做到最好」無法執行。更明確的寫法是：

高頻檢視優先減少閱讀負擔；涉及資料修改的操作，優先保證結果可確認、失敗可恢復。

5. 交付物#

方案評審、線框結構、互動說明和可執行程式碼是不同的交付物。沒有指定時，AI 可能交付一份原則說明，而你需要的是可以操作的頁面。

6. 驗收方式#

「體驗流暢」很難驗證。「查詢失敗後不顯示零值，並保留使用者的篩選條件」可以直接檢查。

角色設定可以補充專業視角，但無法代替以上資訊。「你是頂級設計師」之後，仍然需要具體任務、約束和驗收標準。

四、優秀的軟體設計必須覆蓋正常流程之外的狀態#

設計稿常展示資料充足、網路正常、操作成功的頁面。這有助於討論佈局，卻不代表完整的軟體行為。

Nielsen 的可用性啟發式第一條是「系統狀態可見」：設計應透過適當的回饋，隨時讓使用者知道發生了什麼。[1] 下面用查詢按鈕來說明這一條在實作中的含義。

現象：查詢按鈕背後有一串問題#

  • 發起查詢後，使用者如何知道請求正在執行？
  • 執行期間能否修改篩選條件？
  • 前一個請求晚於後一個請求回傳時，展示哪個結果？
  • 查詢失敗後，是否保留上一次成功的結果？
  • 保留舊結果時，如何說明它不屬於當前查詢？

原因：舊請求可能覆蓋新結果#

React 官方文件把這種情況稱為競態條件（race condition）：兩個請求的回傳順序與發出順序不同，較晚回傳的舊回應覆蓋了新結果。文件給出的做法是，在清理函式裡忽略過期的回應。[7] 瀏覽器的 AbortController 可以取消仍在進行的網路請求。[8]

這兩種做法解決的是「介面展示哪個結果」。它們不改變伺服器端是否已經處理了請求。對讀取類查詢，這通常夠用。對寫入類操作，見下一節。

最後一個問題也容易遺漏。保留舊資料能避免頁面突然清空，但也可能讓使用者誤以為重新整理已經成功。所以「保留舊資料」不是孤立的最佳化，要和狀態說明一起設計。

做法：用狀態表把要求落實#

狀態頁面應表達什麼使用者可以做什麼
首次載入正在獲取資料等待；支援時可取消
有效結果為空查詢成功，當前條件沒有匹配記錄調整或重置篩選
查詢失敗本次結果未獲取成功檢視原因並重試
顯示舊結果當前展示的是此前成功查詢的資料檢視結果時間並重新查詢
權限不足當前帳號無法存取對應資源按產品支援的方式申請權限

空結果、錯誤和沒有權限，不能都用一句「暫無資料」。它們對應不同的事實，也對應不同的下一步。NN/g 討論空狀態時指出，空狀態可以傳達系統狀態，並給出完成關鍵任務的路徑。[2] 錯誤提示則應使用平實的語言，準確指出問題，並給出建設性的解決辦法。[1]

狀態變化也要能被輔助科技感知。WCAG 2.2 的成功準則 4.1.3 要求，不獲得焦點的狀態訊息（例如「載入完成」「查詢失敗」），可以透過程式被輔助科技讀到。[6]

提示詞可以這樣寫：

請補全主要流程之外的狀態設計。

區分首次載入、查詢成功但為空、查詢失敗、顯示舊結果和權限不足。
為每種狀態說明：頁面文案、保留的內容、可用操作和恢復路徑。

對可能同時發起的請求，說明如何避免舊請求覆蓋新結果。
不要讓失敗狀態被呈現為有效的零值或空結果。

五、從軟體副作用理解更深一層的設計#

在程式設計中，副作用通常指執行過程對外部或共享狀態產生的影響，例如寫資料庫、傳送訊息或修改檔案。

在產品設計討論中，可以把視角擴展到操作的連帶影響：重試是否重複執行、刪除後誰受影響、重新整理是否打斷閱讀、通知是否造成重複打擾。

兩種討論有關聯，但不是同一個技術概念。產品側提出風險，仍要由工程側明確狀態、協議和一致性保證。

一個「重新執行」按鈕為什麼不簡單#

設想頁面上有一個失敗任務，使用者點選「重新執行」：

  1. 伺服器端已經建立新任務，但回應在回傳途中逾時。
  2. 頁面顯示請求失敗。
  3. 使用者再次點選。
  4. 如果系統沒有去重機制，就可能建立第二個任務。

此時，「點選後按鈕置灰」只能減少當前介面的重複點選。重新整理頁面、多個瀏覽器視窗、網路重試和其他客戶端呼叫帶來的重複請求，它都擋不住。

HTTP 規範對此有明確的區分。如果一個方法的多次相同請求與單次請求對伺服器端的預期效果相同，它就是冪等的；規範中的冪等方法是 PUT、DELETE 和安全方法，POST 不在其中。客戶端不應自動重試非冪等的請求，除非它能確認請求語意實際上是冪等的，或者能偵測到原請求從未生效。[9]

所以「重新執行」這類通常用 POST 實作的操作，需要額外設計去重。常見做法是冪等鍵（idempotency key）。以 Stripe 的公開 API 文件為例：

  • 它儲存帶某個冪等鍵的首次請求的狀態碼和回應，同鍵的重試會回傳已儲存的回應。
  • 如果同一個鍵對應的參數與原請求不同，會報錯，防止誤用。
  • 在 API v1 中，鍵至少儲存 24 小時後才可能被清理。[10]

這只是一個產品的做法。IETF 有一份 Idempotency-Key 請求標頭的草案，但仍是進行中的工作，尚未成為標準。[11] 採用哪種機制，取決於你的系統。

完整設計要明確：

  • 這次操作如何被唯一識別。
  • 同一次操作重複請求時，是否回傳同一個執行結果。
  • 同一任務是否允許同時執行多個實例。
  • 逾時後如何查詢當前狀態。
  • 失敗後允許重試的是原操作，還是一次新的業務執行。

冪等鍵、唯一約束或執行互斥都可能參與解決問題。只寫下術語，不等於實作了保證。

尤其要區分：同一個請求的重複傳送，與使用者確實希望再次執行任務，是兩種不同的意圖。 一個可行的約定是：同一次使用者意圖的重試，複用同一個鍵；使用者明確再次發起，生成新的鍵。鍵的有效期也要圍繞業務意圖來定。

把副作用變成可審查的設計內容#

操作可能的連帶影響需要明確的設計
重新執行任務重複寫入、資源競爭冪等範圍、併發策略、執行狀態查詢
刪除告警規則後續異常不再通知影響範圍、恢復方式、相關權限
自動重新整理列表閱讀位置或選擇狀態變化重新整理時機、排序穩定性、狀態保留
匯出資料結果與當前頁面範圍不一致匯出條件、時間點、完成回饋
修改統計時區日期邊界和對比視窗變化生效範圍、條件展示、結果解釋

不是每個問題都需要確認彈窗。

  • 低風險操作可以直接完成。
  • 可逆操作可以提供撤銷。
  • 影響範圍大的操作才需要更明確的確認。

這與 Nielsen 的「錯誤預防」一致：要麼消除容易出錯的條件，要麼在使用者提交前提供確認。[1] NN/g 同時提醒，確認框不能濫用，也要寫清後果；更好的做法是讓使用者能夠撤銷。[3] Aza Raskin 的文章對此有更早的論述：能撤銷，就不要彈警告。[4]

確認框要帶資訊。「確定繼續嗎」無法幫助使用者判斷。「將停用這條規則，之後該範圍內的異常將不再傳送通知」才說明了後果。

可直接使用的提示詞是：

請審查這個功能的副作用：[功能描述]。

檢查重複提交、網路逾時、部分失敗、併發操作、取消和重試。
對每個重要場景說明：
觸發條件、可能改變的狀態、使用者可見結果、恢復方式。

區分介面可以緩解的問題和必須由伺服器端保證的問題。
對重複請求明確冪等範圍；對重試明確是否會發起新的業務執行。

按影響程度和出現可能性排序。
優先處理資料正確性和難以恢復的問題，避免為低影響問題增加大量互動。

六、資料看板案例：從數字展示到判斷支援#

下面用一個假設場景，把以上原則連起來。

需求是為資料工程師設計即時業務監控台，展示今日交易筆數、昨日對比、最近完整小時資料、渠道分佈和 ETL 延遲。

如果直接要求「設計一個精美的資料大螢幕」，很容易得到多張數字卡片和幾張趨勢圖。這些內容是否支援判斷，還取決於口徑和狀態是否清楚。

第一步：定義使用者要做的判斷#

使用者先要判斷：業務數值是否值得信任，是否存在需要處理的異常。

所以資料新鮮度不能埋在頁面底部。上游明顯延遲時，業務指標下降可能只是資料還沒到，不能直接解釋成業務變化。

頁面可以繼續展示最近可用的結果，但要清楚標註更新時間和延遲狀態。是否禁用某些操作，要看後果，不能預設把整個頁面鎖住。

第二步：明確可比性#

「今日與昨日對比」至少有兩種含義：

  • 今日截至當前時間，對比昨日同期。
  • 今日截至當前時間，對比昨日全天。

兩種口徑都有用途，但必須寫清楚。今日上午的資料與昨日全天相比，卻只顯示一個下降箭頭，使用者很容易判斷錯誤。

「最近一小時」也要區分：滾動 60 分鐘，還是最近一個完整自然小時。時區不同，日期和小時邊界也不同。

這些不是圖表的附註，而是決定圖表含義的條件。

第三步：讓異常帶著上下文出現#

某渠道交易筆數從 2 筆降到 1 筆，降幅 50%。另一個渠道從 2000 筆降到 1200 筆，降幅 40%。百分比本身不足以決定優先順序。

頁面可以同時展示當前值、對比值、絕對差和相對差。是否告警，要沿用明確的業務規則。樣本很小時，展示樣本量，通常比製造強烈的視覺警報更有解釋力。

不要讓 AI 為了讓頁面「完整」而擅自發明生產閾值。

第四步：把設計轉成可以檢查的要求#

設計一個即時業務監控台，使用者是值班資料工程師。

核心任務：先判斷資料是否可信，再定位業務異常，最後檢視渠道明細。

要求：
1. 明確展示業務時區、資料更新時間和當前查詢條件。
2. 今日對比採用截至當前時間的昨日同期；若介面不支援，說明限制。
3. 最近一小時採用最近一個完整自然小時，並顯示起止時間。
4. 數值為零、查詢失敗和資料延遲使用不同狀態。
5. 變化同時展示絕對差和相對差；分母為零時不偽造百分比。
6. 不改變已有指標口徑，不自行設定生產告警閾值。
7. 重新整理保留篩選條件；舊請求不得覆蓋新條件下的結果。
8. 示範資料明確標註，不暗示已接入真實業務。

交付頁面結構、關鍵互動、狀態表和可執行原型。
對依賴後端實作的保證單獨註明。

這份提示詞的價值在於，它同時約束了佈局、解釋方式和行為，而不只是指定一種視覺風格。

七、視覺提示詞應該描述系統，而不只是裝飾#

視覺品質依然重要。層級不清、對齊混亂、密度失衡，都會增加理解成本。

但「不要用漸層」「不要用圓角」不是通用的設計法則。某種手法是否合適，由內容和場景決定。

比起限制裝飾清單，更值得明確這幾點：

  • 字級層級如何區分標題、主要數值和輔助資訊。
  • 顏色分別表示狀態、分類還是強調，語義是否一致。
  • 哪些內容可以緊湊展示，哪些位置需要留白。
  • 長名稱、大數值、空值和錯誤文案是否破壞佈局。
  • 顏色之外，是否還有文字、符號等識別方式。

最後一條有規範依據：WCAG 2.2 的成功準則 1.4.1 要求，不能只靠顏色來傳達資訊、指示操作、提示回應或區分視覺元素。[5]

例如，監控台可以用緊湊的表格承載任務明細，同時為關鍵異常保留更明顯的空間。不必把每個數字都包裝成同樣大小的卡片。

提示詞可以寫成：

為這個頁面建立一致的視覺規則。

根據使用場景確定資訊密度，定義字型層級、間距、對齊和狀態顏色。
解釋主要視覺規則如何幫助使用者識別重點。

使用長名稱、大數值、空值和錯誤文案檢查佈局。
關鍵狀態不能只依賴顏色區分。
不為裝飾增加無實際資訊的圖表或元件。

八、自我審查有價值，但不能替代驗證#

讓 AI 完成後「找出三個問題並修改」，可以作為第二輪檢查，但數量本身不重要。為了湊滿三個問題而製造無關緊要的修改，同樣會降低效率。

更有效的審查要明確視角和證據：

  • 產品視角：使用者能否完成任務。
  • 互動視角：回饋和恢復是否清楚。
  • 工程視角：狀態變化與併發是否安全。
  • 視覺視角：層級與一致性是否成立。

這些視角可以由同一個 AI 依次執行。「多角色」不等於必須使用多個模型或多個代理。

更重要的是區分「評審發現」和「已驗證事實」。AI 說介面支援取消，不代表已經執行過取消流程。原型裡按鈕置灰，也不代表伺服器端能防止重複執行。

建議使用如下驗收表：

檢查項驗證動作通過標準
查詢條件保留查詢失敗後重試原篩選條件仍在
請求先後順序發起 A 後快速發起 B，讓 A 最後回傳頁面最終保持 B 的結果
錯誤狀態模擬介面失敗明確顯示失敗，不呈現有效零值
重複操作使用同一操作識別碼重複傳送請求符合約定的冪等行為，需驗證伺服器端
結果未知模擬請求逾時但伺服器端已接受可以查詢狀態，不直接斷言未執行
內容極限輸入長名稱和較大數值主要內容可讀，關鍵操作可達

對於可執行的軟體，盡可能實際執行這些場景。對於只交付設計稿的任務，要明確這些是待驗證的要求。

九、把長提示詞拆成幾個有產出的階段#

一次把所有要求塞進提示詞，重點可能被稀釋。可以讓協作逐步推進，但每一步都要有具體產出。

階段產出注意
一、澄清任務主要使用者、核心任務、會改變方案的約束非關鍵的缺失，做合理假設；影響資料口徑、權限或不可逆操作的資訊，要確認
二、確定方向兩種有真實取捨的方案例如異常優先與任務列表優先，而不是僅更換顏色
三、完成實作結構、元件、狀態與操作行為把選定方向落實
四、針對風險驗證驗收表的執行結果先查資料正確性、失敗恢復和高影響操作，再查佈局和視覺細節

小任務可以合併階段。修改一處按鈕間距，不需要重新做一輪產品研究。方法的複雜度要與任務規模匹配。

十、一份可直接複用的綜合提示詞#

以下模板適合軟體頁面、內部工具和資料看板。使用時刪去無關部分，並補充真實約束。

請為下面的需求完成設計並交付可評審結果：
[填寫需求]

【使用情境】
主要使用者：[填寫]
典型場景：[填寫]
最重要的三項任務：[填寫]

【約束】
必須沿用：[元件、介面、權限或指標口徑]
允許調整：[填寫]
當前交付階段：[方案 / 原型 / 可執行實作]

【設計判斷】
先識別最影響使用者完成任務的問題。
需要比較方向時，提出兩種有明確取捨的方案，並推薦一種。
說明選擇依據，只解釋會影響結果的關鍵決定。

【資訊與視覺】
按任務重要性組織內容，明確主要操作與低頻操作。
建立一致的字型、間距、對齊和狀態顏色規則。
使用長文字、大數值、空值和窄螢幕場景檢查佈局。

【互動狀態】
覆蓋載入、成功、空結果、失敗、舊結果和權限不足。
說明操作進行中、結果未知和可重試狀態如何區分。
防止舊請求覆蓋新條件下的結果。

【副作用】
檢查重複提交、部分失敗、併發操作、取消、撤銷和重試。
區分前端緩解措施與伺服器端保證。
明確高影響操作的作用範圍和恢復路徑。
不為低風險操作增加不必要的確認步驟。

【交付與驗證】
交付與當前階段相符的具體結果，不只羅列設計原則。
給出關鍵驗收場景、驗證動作和通過標準。
明確哪些內容已經驗證，哪些仍是假設或依賴後端。
完成後審查高影響問題並修正，不為湊數量製造修改。

缺少非關鍵資料時，做合理假設並繼續。
缺失資訊會改變資料口徑、權限或不可逆操作時，明確指出並確認。

結語：讓提示詞承載判斷依據#

優秀的軟體設計常體現在很小的地方：失敗後保留了使用者輸入，逾時後沒有誤導使用者再次執行，舊資料帶著明確的時間標記，異常資訊提供了足夠的判斷依據。

這些細節很難僅靠「更美觀、更專業」推導出來。它們要被納入任務定義，也要在實作後接受檢查。

提示詞能改善 AI 得到的上下文、約束和評審標準，卻不能代替真實使用者回饋，也不能憑文字建立工程保證。

下一次讓 AI 設計軟體時，先寫清楚四件事：使用者要作出什麼判斷，系統會改變什麼狀態，失敗後如何恢復，以及用什麼證據確認設計有效。 這四個問題，比繼續疊加風格形容詞，更接近設計工作的核心。
