## 寫在前面

李智慧這個名字，很多後端工程師最早是在一本書的封面上看到的：2013 年電子工業出版社出版的《大型網站技術架構：核心原理與案例分析》。後來他在極客時間陸續開了《從 0 開始學大數據》《後端技術面試 38 講》和《李智慧 · 高併發架構實戰課》。按極客時間上的介紹，他做過阿里巴巴技術專家、Intel 亞太研發中心架構師、宅米和 WiFi 萬能鑰匙 CTO，後來任同程旅行交通首席架構師，也給 Apache Spark 貢獻過程式碼。

把這些書和專欄放在一起讀，最強烈的感受是：**他講的東西看起來跨度很大，從 Hash 表、JVM、設計模式，到負載均衡、HDFS、秒殺系統，再到德雷福斯模型，其實一直在用同一種方式拆問題。**

我想用一句話來概括這篇文章的主線：

> **技術世界裡真正需要掌握的原理並不多，它們只是在不同尺度上一遍遍出現。架構師的本事，是在新問題裡認出老原理。**

下面按"方法 → 軟體設計 → 系統架構 → 大數據 → 人"的順序展開，最後談談我認為這些觀點在今天有哪些侷限。

## 一、方法：第一性原理，把"學習"變成"驗證"

《後端技術面試 38 講》的開篇詞就叫《掌握軟體開發技術的第一性原理》。他的出發點是：新技術層出不窮，每次從頭學都很痛苦，以至於行業裡流傳著"35歲以後就不能寫程式碼了"的說法。而他認為"太陽底下沒有新鮮事，絕大多數新技術其實都脫胎於一些既有的技術體系"。

他對理想狀態的描述，我覺得是整個專欄最有價值的一段：建立了自己的技術思維體系之後，再碰到新技術，"這個時候你其實不需要去學習這個新技術了，而是去驗證這個新技術"。也就是先根據原理推導它大概會怎麼實現，再去看文件和程式碼，驗證自己猜得對不對。

落到操作層面，他在《從 0 開始學大數據》的答疑裡給過一個很具體的方法，叫 **5-20-2 法則**：

- 用 5 分鐘瞭解新知識的特點、應用場景和要解決的問題；
- 用 20 分鐘理解它的主要設計原理、核心思想和思路；
- 再花 2 個小時看關鍵設計細節，嘗試使用或者寫個 demo。

每一步過不去就先放下。順序很重要：**先問它解決什麼問題，最後才看細節。**多數人正好反過來，於是知識永遠是孤立的點。

他在同一篇答疑裡還有一句話，我把它當作這套方法的目標：要做工具的主人，而不是工具的奴隸，"最終的目標是要超越 Hadoop，打造適合自己業務場景的大數據解決方案"。

## 二、軟體設計：好程式碼的唯一標準是"能扛住變化"

### 2.1 糟糕的設計會"腐壞"

在《軟體設計的目的：糟糕的程式設計師比優秀的程式設計師差在哪裡？》裡，他給出了一個很鋒利的判斷：**好的設計和壞的設計最大的差別，體現在應對需求變更的能力上。**差的程式設計師害怕需求變更，好的程式設計師歡迎需求變更，因為他們一開始就是針對變更去設計的。

他列了糟糕設計的五個特徵：**僵化性**（改一處牽動一大片）、**脆弱性**（改了這裡，莫名其妙壞了那裡）、**牢固性**（想複用一部分，卻拆不出來）、**粘滯性**（壞的改法比好的改法更容易實施，於是軟體越改越爛）、**晦澀性**（程式碼看不懂，後人只能亂改）。

他用的例子極其樸素：一個把鍵盤輸入複製到印表機的 `copy()` 函式。第一次需求變更要支援紙帶機輸入，加了一個布林變數 `ptFlag`；第二次要支援輸出到紙帶機，又加了 `ptFlag2`，還配了一行註釋"使用前請重置這些flag"。兩次變更以後，一段清晰的程式碼就同時具備了僵化、脆弱、粘滯、晦澀四種病。

解法是把輸入和輸出抽象成 `Reader` 和 `Writer` 介面，`copy` 只依賴介面。有意思的是，用 Go 寫這個例子時，**標準庫已經替你做好了這件事**：

```go
// copyChars 只依赖抽象：任何 io.Reader 到任何 io.Writer。
// 键盘、文件、网络连接、内存缓冲……都不需要改这一行代码。
func copyChars(r io.Reader, w io.Writer) error {
	br, bw := bufio.NewReader(r), bufio.NewWriter(w)
	defer bw.Flush()
	for {
		c, err := br.ReadByte()
		if err == io.EOF {
			return nil
		}
		if err != nil {
			return err
		}
		if err := bw.WriteByte(c); err != nil {
			return err
		}
	}
}
```

`io.Reader`/`io.Writer` 之所以成為 Go 生態裡最成功的兩個介面，原因和李智慧講的完全一樣：它們把"變化的東西"（裝置）和"不變的東西"（複製邏輯）隔開了。

### 2.2 物件導向的本質是多型，框架的本質是依賴倒置

我認為《後端技術面試 38 講》裡寫得最透的是第 12 篇和第 16 篇。

第 16 篇指出，C 語言用結構體和函式指標也能實現封裝、繼承和多型，只是沒有語法和編譯上的約束，很危險。所以他的結論是：**多型才是物件導向程式設計的本質，設計模式的精髓就是對多型的靈活應用。**

第 12 篇講依賴倒置原則，最有價值的一點是他強調了一個很多人忽略的細節：**依賴倒置的關鍵不是"依賴介面"，而是"介面歸誰所有"。**Service 層依賴 DAO 層定義的介面，這不叫依賴倒置；只有介面由高層（Service）定義、低層（DAO）去實現，才算倒置。他的 `Button`/`Lamp` 例子裡，抽象介面叫 `ButtonServer`，歸高層的 Button 所有，"我們從命名上也能看的出來，這正是依賴倒置原則的精髓所在"。

由此他回答了一個看似神奇的問題：為什麼我們的程式不呼叫 Tomcat、Spring 的程式碼，卻能用上它們的功能？因為框架遵循的是好萊塢原則，"Don't call me, I will call you"：應用實現框架定義的介面（比如 `Servlet`），由框架來呼叫應用。

第 17 篇順勢給出了框架和工具的區別：**框架呼叫你的程式碼，工具被你的程式碼呼叫。**Tomcat 是框架，Log4J 是工具。

這裡我想補充一個他在第 7 篇裡沒有展開的觀察。他在講程式語言演化時，把 Go 的隱式介面當作"物件的邊界和封裝性開始模糊"的例子。但從依賴倒置的角度看，**Go 的隱式介面反而讓"介面歸高層所有"變得最自然**：呼叫方可以在自己的包裡宣告一個只含所需方法的小介面，被呼叫方完全不需要知道它的存在，也不用 import 它。Go 社群"在使用方定義介面"的慣例，本質上就是第 12 篇講的介面所有權倒置。同一個原理，在不同的語言裡有不同的落地方式。

## 三、系統架構：高併發是根源，三板斧是手段

### 3.1 大型網站是演化出來的

《大型網站技術架構》第一章畫了一條演化路徑：從單機網站開始，經過應用與資料分離、快取、叢集、讀寫分離、CDN、分散式儲存、業務拆分，最終走到分散式服務。

比路徑本身更重要的是這一章的"價值觀"和"誤區"兩節。價值觀有兩條：**大型網站架構技術的核心價值是隨網站所需靈活應對；驅動大型網站技術發展的主要力量是網站的業務發展。**誤區有三條：**一味追隨大公司的解決方案、為了技術而技術、企圖用技術解決所有問題。**據讀者整理的讀書筆記，這本書的後記還有一句很有名的話：大型網站不是設計出來的，而是逐步演化出來的。

這和第二節講的軟體設計是同一個道理：**不要試圖一次性預測所有變化，而是讓系統在每一個階段都保留應對下一次變化的能力。**

### 3.2 五個要素，以及它們之間的關係

書中第三章提出，除了功能需求，軟體架構還要關注**效能、可用性、伸縮性、擴充性、安全性**五個要素，"架構設計過程中需要平衡這 5 個要素之間的關係"。幾個定義很值得記住：

- **可用性**的前提是伺服器必然會宕機，主要手段是冗餘。
- **伸縮性**指通過往集群裡加伺服器來應對增長；快取叢集加機器可能導致路由失效，需要改進路由演算法。
- **擴充性**直接關注功能需求，主要手段是事件驅動架構和分散式服務。

我的理解是：**伸縮性是對"量"的變化開放，擴充性是對"功能"的變化開放。**後者本質上就是開閉原則在系統層面的版本。

到了《高併發架構實戰課》，他進一步釐清了"三高"的關係：**高併發、高效能、高可用並不是平行的，高併發是根源和核心。**大量使用者同時請求導致資源快速消耗、響應變慢，這是效能問題；效能繼續惡化導致資源耗盡、系統崩潰，這就是可用性問題。

### 3.3 水平伸縮與"三板斧"

應對高併發，他把方案分成兩類：**垂直伸縮**（換更強的機器）和**水平伸縮**（用更多機器組成叢集）。網際網路走的是後一條路，因為它有天然的彈性，可以"一臺伺服器一臺伺服器地新增資源"，而網際網路應用很難提前估計會有多少使用者、在什麼時候來訪問。

在《高效能架構的三板斧》裡，他先給出一個簡單的關係：**吞吐量 = 併發數 ÷ 響應時間**。隨著併發增加，系統依次經歷效能測試區間（吞吐量上升、響應時間基本不變）、負載測試區間（吞吐量見頂後下降、響應時間上升）和壓力測試區間（直到崩潰，吞吐量為 0）。

架構層面的三板斧是：

| 手段 | 解決什麼壓力 | 關鍵點 |
|---|---|---|
| 負載均衡 | 單臺伺服器的併發壓力 | 應用層負載均衡會成為瓶頸；大規模叢集多用鏈路層負載均衡，響應不再經過負載均衡伺服器 |
| 分散式快取 | 讀壓力 | 包括 CDN、反向代理、分散式物件快取；快取只能改善讀，不能改善寫 |
| 訊息佇列 | 寫壓力 | 寫操作非同步化，"削峰填谷" |

但他馬上補了一句，我認為比三板斧本身更重要："不問青紅皂白，不管三七二十一，上來就是三板斧，那做架構師也未免太容易了些。"效能最佳化要從效能測試開始：測出指標，分析瓶頸，最佳化，再測試驗證。

### 3.4 限流器：一個看得見原理的小例子

《限流器設計》這一講以一個叫 Diana 的限流器元件為例，講了四種演算法：固定視窗、滑動視窗、漏桶、令牌桶。他特別指出了固定視窗的缺陷：在視窗邊界前後各來一波請求，短時間內通過的請求數可能是限額的兩倍。

他給的令牌桶虛擬碼有一個很巧妙的地方：**不需要後臺執行緒往桶裡放令牌，取令牌時按時間差"補算"即可。**下面用 Go 實現這兩種演算法，並把"邊界突發"場景跑一遍：

```go
// 固定窗口：窗口切换时计数器清零
func (f *FixedWindow) Allow(now time.Time) bool {
	f.mu.Lock()
	defer f.mu.Unlock()
	if now.Sub(f.winStart) >= f.size {
		f.winStart = now.Truncate(f.size)
		f.count = 0
	}
	if f.count >= f.limit {
		return false
	}
	f.count++
	return true
}

// 令牌桶：按距离上次计算的时间差补发令牌，上限为桶容量
func (b *TokenBucket) Allow(now time.Time) bool {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.tokens += now.Sub(b.last).Seconds() * b.rate
	if b.tokens > b.capacity {
		b.tokens = b.capacity
	}
	b.last = now
	if b.tokens < 1 {
		return false
	}
	b.tokens--
	return true
}
```

限額都設為每秒 100 個請求，在第 0.99 秒和第 1.00 秒各湧入 100 個請求，執行結果是：

```text
fixed window, 10ms 內放行: 200
token bucket, 10ms 內放行: 101
```

固定視窗在 10 毫秒裡放行了 200 個，正是限額的兩倍；令牌桶放行了滿桶的 100 個，加上這 10 毫秒裡新補的 1 個。這也解釋了為什麼他建議"通常場景中優先使用"令牌桶，Diana 的預設演算法也是令牌桶。

### 3.5 秒殺：用架構繞開問題，而不是硬扛問題

秒殺系統 Apollo 的設計，我最欣賞的是它處處體現"不硬扛"：

- 秒殺**獨立部署**，甚至使用獨立域名；
- 頁面走**多級快取**（瀏覽器、CDN、伺服器），重新整理基本打不到伺服器；
- 用一個**不被快取的小 JavaScript 檔案**控制按鈕是否點亮，並下發帶隨機數的下單 URL；
- 每臺下單伺服器只放行少量請求，其餘直接進入秒殺結束頁。

秒殺的核心不是"如何處理一百萬個請求"，而是"如何讓一百萬個請求根本不需要被處理"。

這一講的結尾講了一個故事：某大廠要臨時做一場秒殺，時間太短、併發太高，參會的架構師面面相覷，最後一位架構師站出來接下專案並完成了任務，幾年後晉升為集團副總裁。他的點評是："對一個架構師而言，精通技術是重要的，而用技術建立起自己的信心，在關鍵時刻有勇氣面對挑戰更重要。"

## 四、大數據：同一個原理，換了一個尺度

如果說前面講的是"用更多機器處理更多請求"，那麼大數據講的就是"用更多機器處理更多資料"。他在《後端技術面試 38 講》第 31 篇裡說得很直接：大數據技術是分散式技術在資料處理領域的創新性應用，本質和此前講的分散式技術"一脈相承"。

### 4.1 從 RAID 到 HDFS：垂直伸縮到水平伸縮

《從 0 開始學大數據》第 5 講用 RAID 作為引子：大規模儲存要解決容量、讀寫速度、可靠性三個問題。RAID 在一臺伺服器的多塊磁碟上通過分片併發讀寫和冗餘校驗解決它們，是**垂直伸縮**；把同樣的思想搬到伺服器叢集上，就是 HDFS，是**水平伸縮**。"垂直伸縮總有盡頭，水平伸縮理論上是沒有止境的。"

### 4.2 移動計算比行動數據更划算

第 4 講的核心思想是：程式比資料小得多，所以把程式分發到資料所在的伺服器上執行，而不是把 PB 級的資料搬到程式那裡。各節點的任務程序下載程式包，通過反射載入，再讀取本機的資料分片進行計算。

而第 7 講的標題本身就是一個洞見：**MapReduce 既是程式設計模型，又是計算框架。**開發者只寫 `map` 和 `reduce` 兩個函式，切分、排程、shuffle、容錯都交給框架。

讀到這裡我意識到，**這其實就是第二節講的依賴倒置和好萊塢原則，只是尺度從一個程序變成了一萬臺伺服器。**你不呼叫 Hadoop，Hadoop 呼叫你。下面這個幾十行的 Go 程式把這層關係剝離出來：

```go
type MapFunc func(line string) []KV
type ReduceFunc func(key string, values []int) KV

// "框架"掌握主流程：map -> shuffle -> reduce，用户只提供两个函数
func Run(splits [][]string, m MapFunc, r ReduceFunc) []KV {
	var mapped []KV
	for _, split := range splits { // 真实系统中，每个分片在数据所在的节点上计算
		for _, line := range split {
			mapped = append(mapped, m(line)...)
		}
	}
	groups := map[string][]int{} // shuffle：相同 key 汇聚到一起
	for _, kv := range mapped {
		groups[kv.Key] = append(groups[kv.Key], kv.Value)
	}
	var out []KV
	for k, vs := range groups {
		out = append(out, r(k, vs))
	}
	sort.Slice(out, func(i, j int) bool { return out[i].Key < out[j].Key })
	return out
}
```

對兩個資料塊執行 WordCount，輸出 `[{hadoop 1} {hello 3} {spark 1} {world 1}]`。真實的 MapReduce 複雜得多，但控制權的結構一樣。

而 shuffle 那一步裡的 `map[string][]int`，又回到了他面試過上千人的那道題：Hash 表為什麼是 O(1)。同一個"按 key 分組"的思想，一個在記憶體裡，一個跨越整個叢集。

### 4.3 Spark：同樣的本質，更好的實現

第 13 講的標題是《同樣的本質，為何Spark可以更高效？》。他的回答是：Spark "可以算作是一種MapReduce計算模型的不同實現"，以 shuffle 為界把計算切成多個階段並組織成 DAG，把前一個 Reduce 和後一個 Map 連起來連續計算，並且優先用記憶體儲存中間結果。他還指出，Spark 在 2012 年左右流行，是因為記憶體成本降低了一個數量級，而機器學習又需要大量迭代計算。

**新技術往往不是推翻舊原理，而是在新的約束條件下換一種方式實現它。**

### 4.4 兩種架構模式的對照

在 Hadoop 模組的答疑裡，他指出 HDFS（NameNode/DataNode）、MapReduce 1（JobTracker/TaskTracker）、Yarn（ResourceManager/NodeManager）都是一主多從，並總結出大數據領域的架構模式："集中管理，分佈儲存與計算"。原因是大數據要對資料和任務統一管理；而線上應用的每個請求都相互獨立，為了高效能和便於伸縮，"會盡量避免有全域管理者"。

同樣是分散式，**有沒有全域管理者，取決於任務之間有沒有關聯**。

## 五、人：從高階新手到專家

《技術修煉之道》借用了**德雷福斯模型**：新手、高階新手、勝任者、精通者、專家五個階段。最扎心的結論是：新手會自然進入高階新手階段，但高階新手不會自然進入後面的階段；超過半數的人終其一生都停留在高階新手階段，而"其中一個重要的原因是：高階新手不知道自己是高階新手"。高階新手把規則當作普適真理，精通者則明白"所有的規則都只在特定的場景中才會有效"。他給了三條建議：**勇於承擔責任、在實踐中保持技能（摘"跳起來能夠得著"的蘋果）、關注問題場景。**

《技術落地之道》講了一個隧道車燈的故事：入口立牌"請開啟車燈"，帶來了遊客忘關燈的新問題，幾輪修補之後，最後的解法是在出口寫一句"你的燈亮著嗎？"，**提醒問題的存在，讓該解決問題的人自己去解決。**他還給了一個公式：**問題 = 期望 − 體驗**。

《技術進階之道》畫了一個按二八定律劃分的影響力金字塔，從團隊、公司、全國、全球影響者一路到行業開創者。他提到寫部落格、演講、出書可以作為獲得全國影響力的"捷徑"，但也強調"技術影響力的前提是真正的技術實力"。

《高併發架構實戰課》的結束語寫了一個架構師的一天，總結是："架構師最核心的事情是要控制技術局面，讓事情有節奏地推進"，而"做事情要想看起來毫不費力，必須要在看不到的地方費很大力氣"。

## 六、我的反思：這些觀點的邊界在哪裡

以下是我自己的看法。

**1. 案例帶有鮮明的時代印記。**書中的大量例子來自 Java Web 和 Hadoop 1.x 時代：Servlet、繼承 `TestCase` 的 JUnit 3、JobTracker。原理沒有過時，但需要讀者自己"翻譯"。比如今天很多批處理跑在存算分離的架構上，網路頻寬大幅提升之後，"移動計算比行動數據更划算"不再是一條鐵律，而成了一個需要重新計算的權衡。不過這恰恰印證了他自己的方法：Spark 勝出是因為記憶體變便宜了，存算分離興起是因為網路變快了，**變的是約束條件，不變的是"在約束下做權衡"這件事。**

**2. 有些經驗法則需要還原到場景中。**比如單一職責原則在專欄裡被通俗化為"類檔案儘量不要太大，最好不要超過一屏"，Hash 表也被當作面試的"分水嶺"。作為教學，這些簡化很有效（他自己也承認"O(1)"這個說法並不嚴謹，極端情況下會退化為連結串列）。但按他自己的德雷福斯模型，把規則當作普適真理正是高階新手的特徵。真正值得學的不是"一屏"這個數字，而是"一個類只應有一個引起它變化的原因"背後的耦合觀。

**3. 漏桶並非總不推薦。**他認為漏桶"即使系統資源很空閒"也會一個接一個慢慢處理請求，因此"除非有特別的場景需求"否則不推薦。這個判斷站在"保護自身、最大化利用資源"的視角是對的。但如果你是呼叫方，下游第三方介面要求嚴格平滑的呼叫速率，漏桶的"整形"特性恰恰就是你需要的。**令牌桶限的是總量、允許突發；漏桶限的是速率、消除突發。**選哪個，取決於你在保護誰。

**4. 影響力金字塔有幸存者偏差的風險。**"寫部落格成為全國影響者"的路徑確實存在，但他自己也提醒要有眼光。對大多數人來說，先在團隊內成為出了重要問題會被想到的人，比追求外部影響力更現實。

**5. "演化"不等於"不設計"。**"大型網站是演化出來的"常被誤讀為"不需要前期設計"。但他在《高併發架構實戰課》裡反覆做的恰恰是前期估算，並說"技術指標估算能力是架構師的一個重要能力"。我的理解是：**演化論反對的是過度設計，不反對估算。**知道系統大概會長成什麼樣，才能在當前階段留出恰當的擴充點。

## 七、可以馬上開始做的幾件事

1. **用 5-20-2 法則重學一門你"會用"的技術。**先用一句話寫下它解決的問題，再寫出它的核心原理，最後才去看細節。寫不出第一句，說明你只會 API。
2. **用五個特徵給一段改過多次的程式碼"體檢"。**看到 `xxxFlag` 時，想想 `copy()` 的故事。
3. **檢查一個介面歸誰所有。**挑一個 Service 和 DAO 之間的介面，問問它應該放在哪個包裡。在 Go 裡試著把介面挪到使用方。
4. **給你的系統畫一條效能特性曲線。**壓測出吞吐量和響應時間隨併發變化的拐點，再決定要不要上"三板斧"，以及先上哪一斧。
5. **為入口加上一個令牌桶限流器，並寫清降級策略**，比如 Redis 不可用時降級為本地限流。
6. **開需求會時先問"我們要解決的問題是什麼"**，用"問題 = 期望 − 體驗"檢驗它。
7. **每季度問自己：我在德雷福斯模型的哪一級？**如果今年和去年做的事幾乎一樣，答案多半是高階新手。

## 結語

從一張 Hash 表的按 key 定位，到 MapReduce 的按 key shuffle；從 `copy()` 依賴 `Reader` 介面，到 Tomcat 呼叫你的 `Servlet`，再到 Hadoop 把你的 `map` 函式分發到一萬臺機器上；從 RAID 的多盤併發，到 HDFS 的多機併發。李智慧的寫作反覆示範的，是同一個動作：**把新問題還原成老原理。**

他在開篇詞裡說，如果具體的技術是一朵花，那麼技術思維體系就是一棵樹。對我來說，這篇文章就是給自己的那棵樹修一次枝。
