核心觀點

專家的價值，不只是知道更多答案，而是辨認答案成立的條件，並找出哪項條件一變，原本的最佳解就會失效。場景不是拒絕通用原理的藉口，而是把原理轉成可驗證決策所需的證據。

下文兩個資料情境為原創複合示例，非真實事故或親身經歷；Shopify 案例則依官方工程文章說明。

晨間報表快到交付期限，Spark 作業卻卡在少數幾個任務。資料總量與平日相近，多數執行器已經閒下來，擴大叢集的提議仍很有吸引力：這是最容易解釋，也最像立即採取行動的方案。

可是，若剩下的工作集中在一個尚未被有效拆分的分割區，增加執行器，究竟是在增加運算能力，還是在增加等待那個分割區的人？

我們討論「場景對專家最重要」，不是要把每個問題都回答成「看情況」，而是要分辨：哪些資訊只讓討論更熱鬧，哪些資訊真的會讓我們改變方案。

資料查核：2026-11-18，Asia/Singapore。技術依據採指定版本文件或具日期的官方文章；本文沒有執行效能測試。

一、同樣多的資料，可能是完全不同的工作#

先把開場補完整。這份報表要將交易明細，按商家識別碼與一份大型特徵表做關聯。特徵表在所選快照中，每個商家只有一筆；今天的交易卻大量集中到少數商家。

這個限制很重要：若關聯表同一鍵也有多筆，我們可能面對的是配對筆數膨脹，不只是分配不均。還沒確認鍵的意義與唯一性，就直接套資料偏斜的解法，可能只是更快地算出不該出現的結果。

假設查核後確認關聯語意沒有錯，才來看效能。總輸入量相近，只代表總量這個維度相近。相同關聯鍵的資料集中，可能形成特別大的 shuffle 分割區，讓作業尾端受少數慢任務限制。平均任務時間、平均 CPU 使用率，都可能掩蓋這個分布。

Spark 4.0.1 文件說明，自適應查詢執行（AQE）會利用執行期間統計調整計畫；對支援的 sort-merge join 偏斜處理，則可拆分偏斜分割區，並在需要時複製另一側資料。這項處理須同時啟用 AQE 與偏斜關聯選項，也不是對所有運算、所有資料分布都能自動奏效的保證。1

因此，我們先需要的不是一個神奇的分割區數字，而是實際執行計畫、分割區大小與任務耗時的分布。最慢任務是否也讀了特別多資料？是否有磁碟溢寫？偏斜處理有沒有觸發？如果大多數任務同時在等輸入，瓶頸又可能不在熱鍵。

接下來的選擇才有意義。若計畫符合條件，可以驗證 AQE 的拆分效果；若關聯一側經過正確篩選後足夠小，可以評估廣播關聯。但把一張表廣播到各工作節點之前，仍要確認實際大小與資源承受能力，不能只看它在磁碟上壓縮後有多小。官方文件也明說，關聯提示不保證一定採用指定策略。1

更危險的「優化」，是直接排除最難處理的商家，讓報表準時完成。若這些資料本來就屬於交付範圍，我們改變的不是效能，而是報表定義。這個決定不能藏在一段過濾條件裡。

低成本的下一步，是用保留熱鍵分布的代表性資料，對照原計畫與候選計畫，核對結果，再看尾端任務與完整作業時間。均勻抽樣並不保證能保留熱鍵；若稀釋了熱鍵，測試就可能把真正的問題抽掉。

同一項調整，也不一定適用另一條排程。晨間硬截止的報表，與可以慢些完成、但要節省總資源的歷史重算，對額外複製、網路傳輸與平行度的容忍度可能不同。專業不是選出永遠最快的引擎，而是先說清楚，我們在什麼限制下最佳化什麼。

二、把遲到資料丟掉，系統更快，數字卻可能更不對#

第二個原創情境來自同一批交易事件。營運希望儀表板盡早反映趨勢，容許後續修正；財務需求則設定為：到約定截止點形成可稽核版本，之後的更正要保留調整軌跡，而不是悄悄覆寫已確認的結果。

這是示例中的兩種業務要求，不是所有儀表板與財務系統的通則。它們刻意揭示一個衝突：同一個「正確金額」，可能分別指「目前已知的最佳估計」與「依約定程序確認的結算版本」。

事件發生時間，不等於資料進入處理系統的時間。裝置離線、傳輸延遲或上游補送，都可能讓較早發生的交易比較晚抵達。若我們只按收到時間歸類，計算也許一致，卻未必回答業務原先問的問題。

Apache Beam 以事件時間視窗、watermark 與觸發機制處理這類問題。事件時間是資料元素上的時間戳記；processing time（處理時間）是管線各階段處理該元素時的系統時鐘，兩者不是同一回事。watermark 表達事件時間進度與完整性的判斷：對非啟發式來源，它可提供不會再見到更早事件時間資料的嚴格保證；對啟發式估計而言，越過視窗終點並不是「現實中不會再有舊事件」的證明。允許遲到的範圍、何時輸出，以及是否累積先前資料，是不同的選擇。23

允許遲到也不是「收到每筆資料後再等一段固定時間」，也不是一段 processing time 倒數。在這個模型裡，遲到由系統維護的 watermark 判定；只改一個看似以時間為單位的設定，並不代表就實現了業務要求的等待期限。4

若我們為了讓數字盡早固定，把遲到事件排除，儀表板可能變穩定，卻失去它宣稱涵蓋的交易。反過來，無限延長等待也不能保證終有一天收齊，更會增加狀態保存與維護負擔。

還有一種更隱蔽的錯誤：上游每次輸出修正後的累積總額，下游卻把每次輸出都當成新增加的金額。兩邊單獨看都在正常處理資料，合起來卻重複計算。Beam 2.61.0 的視窗 API 明確區分累積與丟棄已觸發資料的模式；輸出代表什麼，仍須由寫入端與讀取端共同約定。4

所以，專家不能只替團隊填一個遲到容忍值。必須先問：事件時間由誰產生，錯誤的時間戳記如何辨識？晚到的交易要修正歷史視窗，還是進入調整流程？哪些使用者已依先前數字作決定？錯誤可以重算，還是已觸發不可輕易撤回的付款？

這些答案需要資料產生者、營運、財務與工程共同確認。引擎能執行規則，不能替組織決定何時可以把一個估計值當成承諾。財務的截止點也不等於引擎的 watermark，兩者不能因為都與時間有關就混為一談。

最小驗證不必先重建整條資料管線。我們可以準備一組已知應得結果的事件，刻意改變抵達順序，讓部分事件在允許範圍內或之外抵達，再核對儀表板修正與結算調整是否符合約定。超出視窗保留範圍的資料，也要有明確處置，不能誤以為串流引擎會永久替我們等候。4

在營運趨勢場景裡有用的「持續更新」，到了已確認的結算版本，可能變成破壞可追查性的覆寫；為結算設計的保守等待，放到即時觀察又可能失去決策價值。錯的不一定是技術，而是把一種正確性的定義搬到了另一種用途。

三、Shopify 的選擇：需要邊界，不一定需要更多部署單位#

軟體架構也有同樣的誤搬。看到大型程式庫難以修改，我們很容易把問題命名為「單體太大」，接著把微服務當成答案。

Shopify 的 Kirsten Westeinde 在 2019 年官方工程文章中，描述核心 Rails 系統的耦合、測試與新人理解負擔。團隊先調查開發者的痛點，選擇往模組化單體演進：保留單一應用的方向，同時建立業務領域邊界，而不是增加部署單位。5

文章記錄的工作包括按訂單、出貨與帳務等業務概念重組程式，為元件界定介面與資料歸屬，並使用文中所稱的 Wedge 等工具追蹤跨邊界依賴。當時並未完成整個程式庫的依賴隔離，進一步以程式強制邊界也仍在研究規劃，不是已經一次解決的成果。5

這個案例不證明單體勝過微服務。它更有價值的地方，是把兩個常被綁在一起的問題拆開：我們需要更清楚的模組邊界，是否也需要獨立部署與執行？

若主要痛點是找不到依賴、改動影響難以理解，拆成網路服務可能只是把原有耦合搬到網路上，另外增加介面版本與部署協調。Shopify 當時也明確討論了這些代價。5 反過來，若某項工作確實需要獨立擴展、不同發布節奏或較強的執行隔離，僅整理目錄與介面也不會自動滿足要求。

但「拆開就隔離」仍然太快。同用一個資料庫、共享容量，或必須同步發布的服務，未必真能形成我們期待的故障域。部署單位是設計工具，不是隔離效果的證書。

這時更能改變決策的問題是：最近難以完成的變更，到底卡在理解程式、協調發布，還是資源互相干擾？誰有權修改共享資料，誰能拒絕破壞契約的變更？如果組織仍要求所有團隊一起核准，技術拆分是否真的換來自主性？

我們可以先挑一條真實依賴，試著在原應用內建立介面並限制直接存取，觀察問題是否已明顯縮小，再判斷是否值得承擔跨程序成本。這是本文提出的可逆驗證，不是 Shopify 原文保證有效的遷移路線。

專家的經驗應幫我們縮小要測試的假設，不是讓一家公司在某個成長階段的選擇，變成所有團隊必經的成熟階梯。

四、把「以前做過」改成「哪些前提仍然成立」#

前面三個故事，分別改變了資料分布、時間與正確性，以及程式和組織的邊界。它們不是三句「視情況而定」，而是三種可以查證的因果關係：工作是否集中、結果何時被視為定案、拆分究竟消除了什麼耦合。

經驗有價值，是因為它讓我們較快提出這些問題。經驗變成偏見，則是在記憶裡只剩方案，當年那些讓方案成立的條件已經消失。

因此，架構評審不應只有「誰做過最大規模」的競賽。新人可能沒有同等經驗，卻知道資料源最近更換了識別碼、財務不再允許覆寫，或部署權限根本沒有分出去。若只有資深者能定義哪些問題值得問，組織就可能把最接近場景變化的人排除在判斷之外。

我們不必為此寫一份永遠更新不完的背景文件。每項重要決策，可以只留下幾行會改變答案的前提。例如：廣播策略依賴篩選後資料仍可被各節點承受；營運數字允許修正，但結算版本另有調整規則；保留單一部署，是因為目前沒有必須獨立發布的需求。

前提的選擇本身也需要節制。我們不必先理解全部業務才准許修改一行程式。若某項未知不會改變方案、驗證或失敗後的處置，就不應成為評審的門檻。相反地，即使只是一個欄位的定義，只要它決定交易是否被計入，就值得讓有權確認的人明確回答。

再為每項前提接上一個可觀察來源與重議條件：執行計畫或資料分布、資料契約與範例、依賴與發布紀錄。把它放在對應設定、測試或決策紀錄旁邊，比另寫一篇沒人知道何時過期的長文更容易維護。這是本文的工作建議，不是一套已驗證的通用流程。

可維護的場景，不是把所有背景存起來，而是讓下一位修改者知道：什麼訊號出現時，不該照抄這個答案。

五、專家也要知道，什麼時候不能給答案#

若我們只有資料總量，沒有分布與執行計畫，就不該保證加多少資源能準時；若沒有人願意定義遲到交易的歸屬，就不該宣稱某個參數保證業務正確。

拒絕這類保證，不應變成高深莫測的拖延。我們仍可以給出候選解釋、需要的最少證據，以及最便宜的反例測試。專業的暫停，是把不確定性變成下一步，而不是要求別人先交出一個完美世界。

這也不表示每次都要重新發明。資源有限、跨程序呼叫可能失敗、重複輸出必須有一致的解讀，這些原理仍能遷移。場景決定我們如何滿足它們，不會把它們取消。敏感資料的存取控制，更不能因為測試很急或團隊很小就被略過。

AI 可以協助列出方案的反例、比對文件與設定、檢查哪些假設還沒有證據。但它不知道未提供的私有業務規則，也不能因為生成了一份完整建議，就視為已辨認所有限制。比較有用的問法不是只請它選技術，而是請它指出：哪項未知一旦答案不同，就會推翻目前建議；我們再用真實資料與負責人的確認去核對。

結語：我們是在遷移知識，還是在複製信心？#

把成功方案帶到新地方，是工程工作的重要能力。但真正值得遷移的，不只是設定、框架與架構圖，還包括判斷依據、失效條件，以及如何發現自己判斷錯了。

專家不是只懂業務，也不是只懂原理；我們需要用原理辨認限制，再用場景決定哪些代價值得承擔。權威若能讓假設更容易被質疑，經驗才會成為團隊資產，而不是後來者不敢碰的答案。

下一次有人說「以前就是這樣解決的」，我們可以先問：如果今天只能驗證一項前提，哪一項一旦不成立，就足以讓我們撤回這個最有把握的方案？
